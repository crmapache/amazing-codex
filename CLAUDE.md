# Amazing Codex GUI - заметки для работы с проектом

Плагин для JetBrains IDE: чат-панель для OpenAI Codex внутри IDE. Это порт
[Amazing Claude Code GUI](https://github.com/crmapache/amazing-claude-code) (соседняя папка
`../amazing-claude-code`) на Codex: интерфейс (`webview/`) - тот же код, движок под ним (`src/`)
переписан под `codex app-server`.

Заметки оригинала про саму панель (лента, поле ввода, харнесс, телефон, поиск, сценарии, словари,
статистика) лежат в `docs/panel-notes.md` и остаются верными - это тот же код. Всё, что там сказано
про Claude Code CLI, к форку не относится; как это устроено у Codex - ниже.

## Правила проекта

- **Git-коммиты только с явного разрешения на каждый конкретный коммит.** Правки в рабочем дереве
  можно делать свободно; перед `git commit` - остановиться и спросить.
- **Секреты.** `.env` и `secrets/` в форк не копировались. Если появятся - те же правила, что в
  оригинале: `.env` не читать ни целиком, ни кусками, значения не печатать.
- **Порты** - из `~/.claude/ports.md`: dev-сервер панели и харнесса - `5190` (`webview/vite.config.ts`,
  `strictPort`), телефонный клиент - `5191`, релей локально - `4450`, приёмник отзывов - `4451`,
  отладочный порт панели в песочнице - `4452` (`./gradlew runIde -PjcefDebugPort=4452`).
- **Запущенное гасить по PID**, не `pkill -f <слово>`: на машине рядом живут песочницы оригинала.
- **Оригинал не трогать.** `../amazing-claude-code` - отдельный проект с незакоммиченной работой.
  Одно исключение по решению владельца - сервис статистики `usage-service/` там: он общий для обоих
  плагинов (поле `product`: `acc` / `acx`, вкладки в админке), и его тест `codexFork.test.ts` сверяет
  списки с `usage/UsageFeatures.kt` форка.

## Главное решение: переводчик, а не второй интерфейс

Codex говорит своим протоколом (JSON-RPC `app-server`: `thread/*`, `turn/*`, `item/*`), а панель,
телефон, статистика, сценарии, поиск и журнал разговоров умеют читать один язык - события потока
Claude Code (`system/init`, `assistant` с блоками `text`/`thinking`/`tool_use`, `user` с
`tool_result`, `stream_event`, `result`, `rate_limit_event` и т.д.). Поэтому между Codex и всем
остальным стоит слой перевода, а всё выше него не менялось:

- `codex/AppServer.kt` - процесс `codex app-server` и клиент JSON-RPC поверх stdin/stdout.
  Сообщения без поля `jsonrpc`; рукопожатие `initialize` (с `capabilities.experimentalApi = true`),
  потом уведомление `initialized`; запросы до конца рукопожатия ждут в очереди.
- `codex/CodexDialect.kt` - чистые функции: предмет Codex -> строки потока в диалекте панели.
- `codex/CodexStream.kt` - живой переводчик одного хода: дельты текста и рассуждений, начало и конец
  предметов, план, счётчики токенов, повторы, конец хода.
- `codex/CodexSession.kt` - один разговор: публичное API то же, что было у `ClaudeSession`, поэтому
  `CodexSessions`, хаб, очередь, телефон и сценарии работают с ним без изменений.

Правило для правок: **новое поведение Codex переводится в существующий диалект, а не протаскивается
в панель новым типом сообщения.** Панель и телефон - общий код, и новый тип пришлось бы учить трём
клиентам. Исключения делались только там, где у диалекта не было места для факта: `unified_diff` у
правки (см. ниже) и уровни усилия у модели в сообщении `models`.

### Процессы

- **Один `app-server` на разговор** (`CodexSession`). Тред открывается `thread/start`
  (`thread/resume` для разговора из истории, `thread/fork` для форка); брифинг панели
  (`CodexLaunch.PANEL_BRIEFING`) уходит как `developerInstructions`.
- **Один общий `app-server` для вопросов не про разговор** (`CodexCatalog`): список тредов, страницы
  истории, агенты workflow. Поднимается на первый вопрос, гаснет после двух минут тишины. Звать только
  не с EDT (`call` проверяет).
- **Разовые запуски** (`CodexOneShot`): вопрос про аккаунт в его окружении (`account/read`,
  `account/rateLimits/read`, `model/list`) и одноразовый ответ модели - эфемерный тред, read-only,
  `approvalPolicy: never`, свои `baseInstructions` вместо инструкций агента, при нужде `outputSchema`.
  На нём стоят улучшение промпта (`PromptImprover`), ИИ-поиск (`search/AiSearch`), названия вкладок
  (`CodexTitles`) и написание сценария (`scenario/ScenarioAuthor`). В историю они ничего не пишут.
- Процесс, разговор которого простоял полчаса, отдаётся (`IdleSleep`, как в оригинале); следующее
  сообщение поднимает тред через `thread/resume`.
- **Писатель у треда один** (замер 0.163): `thread/resume` треда, который держит другой живой процесс, Codex
  отбивает «thread … already has an active writer». Остановка панели (`AppServer.stop`: закрыть stdin, через 3 с
  SIGTERM, обёртка `codex` на node его передаёт) отпускает тред сразу: на конце ввода старый процесс обрывает ход
  (`turn_aborted` в файле треда) и уходит меньше чем за секунду, новый поднимается над тем же тредом, хода
  восстановления Codex не запускает. SIGKILL обёртки, наоборот, оставляет родной `app-server` сиротой, и тот держит
  тред до конца своего хода. Поэтому процесс разговора гасится только через `stop`: на этом стоят переезд на другой
  аккаунт, перезапуск после `/config` и MCP и возврат закрытой вкладки.

### Как предметы Codex становятся карточками

| Предмет Codex | Карточка в ленте |
|---|---|
| `agentMessage` (+ `item/agentMessage/delta`) | текст ответа |
| `reasoning` (+ `summaryTextDelta`/`textDelta`) | мысли |
| `commandExecution` с одним действием `read` / `search` / `listFiles` | `Read` / `Grep` / `Glob` |
| `commandExecution` прочее | `Bash` (команда без обёртки `/bin/zsh -lc '...'`, `CodexDialect.unwrapShell`) |
| `fileChange`: `add` / `delete` / `update` | `Write` / `Edit` с `deleted` / `Edit` с `unified_diff` (и `moved_from`); результат на файл со структурной половиной |
| `mcpToolCall` | `mcp__<сервер>__<инструмент>` |
| `webSearch` | `WebSearch` |
| `imageView` | `Read` картинки |
| `collabAgentToolCall` | `Task` (субагент) |
| `plan` (ход в режиме плана) | `ExitPlanMode` - карточка плана с кнопками |
| `turn/plan/updated` | `TodoWrite` - полоса задач над полем |
| `contextCompaction`, `thread/compacted` | строка компакта |
| `error` с `willRetry` | `api_retry` - карточка повтора |
| `model/rerouted` | `model_refusal_fallback`, причина словами (`CodexDialect.rerouteReason`) |
| провал хода по входу | ответ `<synthetic>` с `authentication_failed` - строка с кнопкой входа |
| провал хода по лимиту | `rate_limit_event` (окно и сброс - из последнего `account/rateLimits/updated`) и ответ `<synthetic>` с `rate_limit`, как у Claude Code |

- **Правка рисуется из диффа, который применил Codex**, с настоящими номерами строк
  (`unified_diff` во входе `Edit`; `feed/tools.ts` - `unifiedHunks`, `countUnified`). `old_string` и
  `new_string` рядом всё равно собираются (`CodexDialect.editInput`): по ним считает строки
  статистика, и их рисует телефон, собранный до этой правки.
- **Патч на несколько файлов - несколько карточек**: id предмета, дальше `id:0`, `id:1`
  (`CodexDialect.fileCallIds`). **И несколько результатов, событие на файл** (`CodexDialect.resultLines`), у каждого
  структурная половина `{filePath, type: create|update|delete, movedFrom?}` (`fileHalf`): по ней список изменённых
  файлов хода (changed-files.md) считает строки и откатывает их, а хунки берёт из `unified_diff` карточки - третьей
  копии диффа нет. У субагента вызова в ленте нет, и его половина несёт сам дифф (`parent_tool_use_id` карточки).
- Результат команды режется до 30 000 символов; отклонённое человеком - `Declined.`.

### Запросы к человеку

| Запрос сервера | Что видит панель | Ответ |
|---|---|---|
| `item/commandExecution/requestApproval` | разрешение на `Bash` | `accept` / `acceptForSession` / `acceptWithExecpolicyAmendment` / `decline` |
| `item/fileChange/requestApproval` | разрешение на `Edit`/`Write` | `accept` / `acceptForSession` / `decline` |
| `item/tool/requestUserInput` | вопрос с вариантами (`AskUserQuestion`) | ответы по id вопросов |
| `item/permissions/requestApproval` | разрешение `Permissions` | выданные права, на ход или на сессию |
| `mcpServer/elicitation/request` | разрешение `mcp__<сервер>__open` | `accept` / `decline` |
| конец хода в режиме плана с предметом `plan` | карточка плана | одобрение - режим «Авто» и ход «Implement the plan.» |

**Конец хода с планом придерживается до решения** (`CodexSession.heldPlanTurn`). Codex заканчивает ход
вместе с предметом `plan`, а панель (кнопки карточки, «ответ на план» из поля, телефон) считает план
вопросом внутри идущего хода и гасит кнопки на `result`. Поэтому `turn/completed` такого хода не
переводится, пока план не решён: одобрение, «Keep planning», Stop, новое сообщение мимо плана или смерть
процесса отпускают его (`releasePlanTurn`). Без этого план нельзя было одобрить вовсе (найдено живьём).
Ход, о котором просит решение, говорится тем же проходом хаба, что и очередь, и раньше неё (`Outgoing.afterPlan`,
turn-lifecycle.md). **Переезд на другой аккаунт план не снимает, а уносит в новый процесс** (`CodexSession.HeldPlan`,
`handOverPlan`/`adopt`): ход Codex уже кончен, и решить план может любой процесс над тем же тредом (accounts.md).

Идентификатор запроса для панели - свой (`codex-<эпоха процесса>-<id>`): id JSON-RPC начинаются
заново у каждого процесса, и без эпохи ответ на карточку, пережившую перезапуск, ушёл бы чужому
запросу. **Эпоха - один счётчик на всю IDE** (`CodexSession.PROCESS_EPOCHS`), а не свой у разговора:
реестр карточек проекта (`SessionPermissions`) держит их по одному id, и у каждого нового разговора
первый вопрос был `codex-1-0` - «Allow» на одной вкладке (за столом или с телефона) отвечал на команду
другой (поймано съёмкой картинок: три свежих разговора, первый стоял, третий выполнил команду, которую
никто не разрешал). Таймеров в пути разрешений нет, как и в оригинале: вопрос ждёт человека сколько угодно.

### Режимы, модели, усилие

Режим (`PermissionModes.kt`) - это пара «политика одобрений + песочница», id сохранены от оригинала,
потому что их называют сохранённые настройки и телефон:

| id | На экране | approvalPolicy | sandbox |
|---|---|---|---|
| `manual` | Ask every time | `untrusted` | workspace-write |
| `acceptEdits` | Auto | `on-request` | workspace-write |
| `readOnly` | Read only | `on-request` | read-only |
| `plan` | Plan | `on-request` | read-only + `collaborationMode: plan` |
| `bypassPermissions` | Full access | `never` | danger-full-access |

- Старые значения из настроек оригинала читаются (`normalize`): `default` -> `manual`, `auto` и
  `dontAsk` -> `acceptEdits`, незнакомое -> `acceptEdits`.
- Режим, модель и усилие едут с каждым `turn/start`, поэтому смена работает посреди разговора без
  перезапуска процесса и применяется со следующего хода.
- **Одобренный план переводит разговор в «Авто», и за столом, и с телефона** (`decidePlan`). В
  оригинале за столом был «без вопросов»; у Codex ближайшее - полный доступ без песочницы и с сетью,
  это намного больше, чем одобряет план.
- Модели - из `model/list` (`CodexShapes.models` -> `ProjectUsage.sendModels`). В меню сверху всегда
  стоит «Default»: список Codex называет только модели, а вкладка без выбора работает на `default` (в
  `turn/start` модель тогда не передаётся). Подпись под ним называет модель с `isDefault`.
- **Модель хода Codex держит «for this turn and subsequent turns»**, поэтому возврат на «Default» после
  выбора едет явной моделью по умолчанию, один раз (`CodexSession.modelOnWire`, `defaultModel`: что Codex
  назвал на `thread/start` без модели, иначе `model` конфига, иначе `isDefault` каталога аккаунта). Молча
  вкладка оставалась на выбранной модели, а подпись называла модель открытия треда.
- **Ответы подписаны тем, на чём идёт тред, а не выбором** (`threadModel`, `signedModel`): ответ на открытие
  треда, модель, которую понёс `turn/start`, и `threadSettings.model` из `thread/settings/updated` (приходит,
  когда ход меняет настройки, замерено на 0.163). Выбор посреди хода доезжает только со следующим
  `turn/start`, поэтому остаток хода подписан старой моделью, и панель судит выбор только после конца хода, в
  котором его сделали (`ownSwapDue` на `result`, не на результате инструмента). После `model/rerouted` до
  конца хода ответы подписаны моделью перенаправления (`CodexStream.answeringModel`, по `turnId`).
- **Уровни усилия - свои у каждой модели**: у `gpt-5.5` нет `max` и `ultra`, и умолчание у неё
  `xhigh`. Codex принимает недоступный уровень молча и работает на другом (проверено живьём), поэтому
  меню показывает только уровни модели (`levelsOf`, `effortOptions` в `catalog.ts`), а смена модели на
  ту, где выбранного уровня нет, сбрасывает усилие на `auto` (`pickModel` в `App.tsx`, та же логика в
  `mobile/screens/RunSheet.tsx`). Уровни Codex 0.152: `low`, `medium`, `high`, `xhigh`, `max`, `ultra`
  (+ `minimal` у старых моделей); `ultracode` из настроек оригинала читается как `ultra`.
- **Быстрый режим** (из ACC 0.13.43; подробно - `.claude/rules/models.md`, «Быстрый режим») - уровень обслуживания
  Codex `priority` («Fast» в каталоге, `ServiceTiers`). Просьба трёхзначная (`CodexSession.fastMode: Boolean?`):
  null - как в конфиге Codex, true - `priority`, false - `default`. Новая вкладка начинает с null (ни умолчания, ни
  закрепления: платную скорость панель сама не включает и `service_tier` конфига не перебивает); дальше просьба
  живёт с разговором - форк, переезд на другой аккаунт, возврат закрытой вкладки, перезапуск IDE
  (`SessionLaunch.fast`, `TabMemory.Tab.fast`). Едет `serviceTier` у `thread/start|resume|fork` и у каждого
  `turn/start` (`tierOnWire`), потому что **тир не переживает процесс** (замер 0.163: ход держит тир для следующих
  ходов, но `thread/resume` в новом процессе встаёт на тир конфига). **Правду говорит Codex**: тир из ответа на
  открытие треда и из `thread/settings/updated`, а IDE переводит его в `fast_mode_state` /
  `fast_mode_disabled_reason` на `system/init` и каждом `result` (`fastReport`). Знак ↯ горит и когда режим из
  конфига Codex (`fromSettings`); причины - только для просьбы панели: `pending` (просьба новее последнего хода,
  который её нёс), `model_not_allowed` (у модели нет уровня по каталогу), `not_served` (Codex ответил другим тиром).
  Отказа у Codex нет вовсе: недоступный уровень он молча выбрасывает из запросов. Каталог - `serviceTiers` у
  `model/list` (`CodexShapes.models` -> `supportsFastMode`, описание уровня цитируется как есть); конфиг сильнее
  каталожного `defaultServiceTier` (замер 0.163). Меню MODEL, `/fast [on|off]`, шторка телефона (`setFastMode`
  телефону разрешён).

### Команды в поле

`app-server` слэш-команд не знает, поэтому их разбирает IDE (`CodexCommands.parse`):

- `/compact` -> `thread/compact/start`; `/clear` и `/new` -> новый тред в той же вкладке и
  `conversation_reset` панели; `/init` -> ход с текстом `CodexLaunch.INIT_PROMPT`; `/review [ветка |
  commit <sha> | инструкции]` -> `review/start` (без аргумента - незакоммиченные изменения).
- `/prompts:<имя> аргументы` - свой промпт из `~/.codex/prompts/<имя>.md`, раскрытый с `$1..$9`,
  `$ARGUMENTS`, `ИМЯ=значение`.
- `/<скилл>` или `$<скилл>` - скилл уходит предметом `skill` рядом с текстом (реестр - `CodexSkills`,
  наполняется сканом `CodexCommandHints`: `.codex/skills`, `.agents/skills` и общая
  `.claude/skills` проекта, `~/.codex/skills`, `~/.agents/skills`). До открытия треда панель также
  регистрирует `.claude/skills` в `app-server` через `skills/extraRoots/set`: поэтому этот же живой
  каталог видит сама модель, а не только меню `/`; старый `app-server` без метода мягко откатывается
  к явному вызову из меню.
- Слэш-команда, отправленная посреди хода, ждёт его конца (`PromptDelivery.waitsForTheTurn`), а
  обычный текст посреди хода уходит в идущий ход через `turn/steer` (с `expectedTurnId`; не
  принялся - ждёт конца хода и говорится на нём первым, раньше очереди хаба - `CodexSession.unsent`,
  `CodexSessionHub.sayNext`).
- `/status` - команда панели (ACC 0.13.43): строка с id треда и командой для терминала `codex resume <id>`; у вкладки
  на добавленном аккаунте на macOS и Linux перед ней ящик (`CODEX_HOME=… CODEX_SQLITE_HOME=…`, `ResumeLine`), на
  Windows - честная подпись «продолжит на входе по умолчанию». Набранный на телефоне `/status` IDE отвечает той же
  строкой, а не отдаёт модели (`SessionCommands.statusAsked`). Правый клик по панели - «Copy Session ID»
  (`PanelContextMenu`). Подробно - session-info.md.
- `/fast [on|off]` - быстрый режим этого разговора (см. «Режимы, модели, усилие»).
- `/rename имя` - имя треда в записи Codex (`thread/name/set`) и вкладки. За столом панель делает его
  сама (поле на вкладке), `CodexCommands` разбирает его для телефона.
- `/btw вопрос` и `/side вопрос` - вопрос сбоку (см. ниже); `/config` без аргумента - экран настроек
  Codex, `/config ключ=значение` - запись одной настройки.

### Общий `.claude`

`.claude` проекта остаётся единым источником AI-конфига для Claude Code и Codex, без импортированной
копии в `.codex`. Каждая `CodexSession`, включая головы и карточки сценариев, дополняет свою роль
коротким контрактом `ClaudeProjectConfig`: в начале задачи посмотреть имена и frontmatter правил,
прочитать только подходящие по теме или `paths`, а при работе с агентами, workflow, хуками, настройками
и остальным AI-конфигом брать исходник прямо из `.claude`. Тела всех правил заранее в developer
instructions не складываются, иначе общий контекст расходовался бы ещё до первого вопроса.
Контракт помечен версией в developer instructions; при возобновлении старого треда без этой метки
панель один раз добавляет актуальные инструкции developer-сообщением до следующего хода.

`settings.local.json` при этом не становится разрешением Codex: права по-прежнему задаёт выбранный в
панели MODE. Это важно, потому что Claude allowlist и политика `app-server` означают разные вещи.

### Вопрос сбоку (`/btw`, `/side`)

У терминала Codex это `/side` - «side conversation in an ephemeral fork», экран TUI, а не метод
`app-server`. Панель повторяет его рецепт (`SideQuestion`, `CodexSession.askAside`):
- эфемерный `thread/fork` треда вкладки в её же процессе (`ephemeral` + обязательный `excludeTurns`),
  read-only, `approvalPolicy: never`, через `config` выключены субагенты (`features.multi_agent`),
  встроенные приложения Codex и серверы плагинов (`features.apps`, `features.plugins`) и по имени - только
  серверы из таблицы `mcp_servers` конфига (спрашивается `config/read` перед форком). Имя без таблицы
  (`codex_apps`) Codex принимает за сервер без транспорта и не грузит конфиг вовсе - так `/btw` падал; инструкции разработчика и граница - дословно тексты `/side` из бинаря Codex;
- `thread/inject_items`: граница сообщением developer, потом прошлые вопросы и ответы нити парами;
  не принял - те же слова уходят перед вопросом текстом (`SideQuestion.inlined`);
- `turn/start` с вопросом и `summary: none`; события чужого треда уводятся в `asideNotification`;
- **новая копия на каждый вопрос**: нить держит клиент и забывает её молча, а телефон с релея не умеет
  сказать «забудь»; после ответа `thread/unsubscribe`;
- отмена и таймаут 660 с - `turn/interrupt`; остановка процесса - всем `failed/ended`; разговор без
  треда на диске - эфемерный `thread/start` без истории; форк посреди хода Codex делает (проверено
  живьём на 0.152), не принял - через `lastTurnId` последнего законченного хода.

### Контекст редактора

Открытый файл и выделение уходят **вторым text-элементом** `turn/start`/`turn/steer` после слов
человека, в формате `/ide` терминала Codex (`IdeContextPrompt`: «# Context from my IDE setup:», «##
Active file:», «## Active selection range:», «## Active selection of the file:») - модель обучена на
нём. В истории `CodexDialect.userContextOf` отделяет этот элемент, а `userPrompt` кладёт его блоком в
словах, которые читает `feed/editorContext.ts`. Превью треда в `thread/list` склеивает части сообщения
**без разделителя** (замерено) - строка истории режется по заголовку; поиск вырезает блок целиком.

Чип файла в поле (ACC 0.13.43) - меню: слать с каждым сообщением, не слать с этим, не слать никогда. «Только с этим
сообщением» при выключенной настройке едет своим флагом `editorOnce` у `prompt`/`queuePrompt`
(`EditorContext.goesWith`, `EditorOnceTest`): хаб держит голый флаг `editor` под настройкой, и эта проверка молча
съедала явный выбор человека - агент файла не получал, а карточка писала, что он ушёл. Ловушка была и в оригинале
(editor-context.md).

### Настройки Codex и доверие проекту

- Экран `/config` (`CodexConfig`, `CodexConfigDesk`, панель - `CodexConfig.tsx`): чтение -
  `config/read {cwd, includeLayers}` (значения, `origins` - откуда значение, слои) +
  `configRequirements/read` (что разрешила организация) + `experimentalFeature/list` (стадии beta /
  experimental как `features.<имя>`); запись - `config/batchWrite` с **явным путём** к настоящему
  `~/.codex/config.toml` (в ящике аккаунта это символьная ссылка) и `expectedVersion`. Codex отвечает
  `ok` на значение, которое перебивает слой проекта (замерено), поэтому после записи конфиг читается
  снова, и перебитое значение помечается `overridden`. После записи живые разговоры всех проектов
  поднимаются заново между ходами (`restartAll`): многое Codex читает при старте процесса.
- **Доверие**: слой проекта (`.codex/config.toml`, хуки, exec policies) Codex грузит только у
  доверенного проекта (`[projects."<путь>"] trust_level`). Терминал Codex спрашивает это при первом
  запуске в папке, панель не спрашивала никогда. Теперь: блок «This project» наверху экрана настроек
  (кнопка Trust / Stop trusting, запись upsert'ом объекта `projects` - путь с точками ломал бы ключ) и
  строка в ленте раз на разговор, если у проекта есть свои настройки, а доверия нет
  (`CodexSessionHub.checkProjectSettings`, `accountOutranked` с `reason: untrusted`). Телефону
  `setProjectTrust` запрещён.
- Доверенный проект может требовать способ входа или рабочее пространство (`forced_login_method`,
  `forced_chatgpt_workspace_id`): Codex тогда считает вход аккаунта отсутствующим **в этой папке**.
  Строка в ленте (`reason: account`) и объяснение на экране входа (`heldBackBy` в сообщении `auth`)
  вместо бесполезного «войдите снова» (`CodexConfig.demands`).
- Каждым ходом панель шлёт `sandboxPolicy` с `network_access` / `writable_roots` / `exclude_*` из
  `[sandbox_workspace_write]` конфига, а `summary` - только если конфиг не задаёт
  `model_reasoning_summary` (`CodexConfigDesk.workspaceWrite`, кэш на 5 минут, греется на старте
  процесса). `CodexSettings` (режим новой вкладки) читает слой проекта только у доверенного и в
  порядке Codex: проект, человек, система.
- Подпись «Default» в меню модели - модель из `model` конфига, если она в каталоге, иначе `isDefault`
  Codex; «auto» усилия - `model_reasoning_effort` конфига, если модель его умеет (`CodexShapes.models`).

### Сценарии под Codex

- Голова, поднятая в другую роль над тем же тредом (подхват карточки и обратно), получает новую
  инструкцию **сообщением developer через `thread/inject_items`** (`CodexSession.roleChange`):
  `thread/resume` поле `developerInstructions` принимает и игнорирует (замерено: тред, начатый «по-
  французски», после resume с «по-немецки» отвечал по-французски; после inject - по-немецки).
- Ход, остановленный посреди реплики, Codex не завершает `item/completed`, и в файле треда её нет вовсе
  (замерено); `CodexStream` держит набранные дельты и при конце хода кладёт недописанную реплику в ленту
  как есть, иначе панель стирала то, что человек уже читал. После `exitedReviewMode` Codex 0.152 повторяет
  находки обычным `agentMessage` - повтор пропускается (`reviewSaid`, в живом ходе и в истории).
  `/compact` помечается ручным (`compactionAsked` -> `trigger: manual`).
- `CodexStream` выпускает `content_block_start` на каждый `agentMessage` (живая строка карточки не
  склеивает реплики, `LiveWords`) и `message_delta` с `end_turn` после ответа с `phase: final_answer` и
  на предмет `hookPrompt` (хук Stop вернул агента в работу) - голова видит все концовки хода
  (`TurnEndings`).
- **Фоновые помощники карточки** (из ACC 0.13.23). Codex запускает субагента (`collabAgentToolCall`
  `spawnAgent`) в своём треде и **никогда не будит породивший тред**, когда тот закончил (замерено на
  0.160: ход с `spawnAgent` кончился сразу, ход субагента - через полминуты, родителю ничего). Поэтому
  `CodexSession` карточки (`onBackground`, только у сценария; у вкладок не включено - панель ждала бы хода,
  который не придёт) говорит старт и конец работы каждого субагента строками `task_started` /
  `task_notification` диалекта (`CodexDialect.taskStarted`) - их читает `BackgroundWork`, общий с
  оригиналом. Конец хода при живых помощниках - ожидание (как в оригинале), а когда все закончили, движок
  сам просит карточку собрать их ответы (`ScenarioEngine.helpersFinished`, `HeadTalk.HELPERS_FINISHED`) -
  у Claude Code это делал сам CLI. Пауза прогона останавливает и субагентов карточки (`interruptHelpers`),
  чтобы слова «помощники не пережили остановку» были правдой.
- **Отказ по лимиту двигает прогон на другой аккаунт** (из ACC 0.13.28, `LimitRelief`) - движок узнаёт
  отказ по ответу `<synthetic>` с `rate_limit` (`AgentStream.isLimitRefusal`), поэтому переводчик говорит
  его так же, как Claude Code. Окно в `rate_limit_event` - `five_hour` / `seven_day` по длине полного окна
  (`CodexShapes.stoppedWindow`): Codex называет причину (`rate_limit_reached`), а движок записывает отказ
  против аккаунта только для общих окон (`AccountUsage.SHARED_WINDOWS`).

### Откат к сообщению и точные форки (из ACC 0.13.18 / 0.13.21)

- **Разговор режет сам Codex**: `thread/revert {threadId, beforeTurnId}` (появился в 0.160) выбрасывает ход
  сообщения и всё после него; агент отрезанного не помнит (замерено). Идущий ход сначала останавливается
  (`CodexSession.stopForRewind`), ревёрт под ходом Codex не делает. Остальное - работа сессии, как у
  оригинала были служебные запросы CLI (`CodexSession.rewind`): какой ход начало сообщение (`turnOf` - имя
  панели из `turnOfMessage` для отправленных в этом запуске, id предмета `userMessage` для прочитанных из
  истории), «разговор ушёл вперёд» (`movedPast` по списку отданных сессией сообщений - сообщение с телефона,
  пришедшее при открытом диалоге, останавливает откат), сообщение посреди хода (`MID_CALL`).
- **Код возвращается откатом патчей**, а не копиями: копий Codex не ведёт, а каждый применённый патч лежит в
  треде целиком (`fileChange`: текст файла у `add`/`delete`, unified diff у `update`, `move_path` у
  переноса, после диффа переноса Codex дописывает «Moved to: …» - читается по счётчикам заголовков хунков).
  `CodeRewind.plan` разворачивает их от новых к старым в памяти тем же движком, что откат из списка файлов хода
  (`ChangeRevert`, по ходам и по файлам, с его поблажкой «уже откачено»: ход, откаченный из списка, при откате к
  сообщению до него не читается «изменённым»; ход этого запуска IDE, сверенный с диском, откатывается тем, что на
  деле сделал - `TurnFiles.Settled`). Файл, изменённый после патча чем-то другим (командой, человеком), по-прежнему
  останавливает возврат кода до записи (`Rewind.Code.Changed`, своё состояние диалога `changed`). Откат одного кода
  разговор помнит, поэтому агенту перед следующим ходом говорится, какие файлы вернулись (`PutBack`).
  Порядок «оба»: проверка кода → остановка хода → проверка снова → ревёрт → запись файлов.
  Настройки «чекпоинтов» у Codex нет, поэтому состояния `off`/`notTracked`/`noCheckpoint` форк не шлёт.
  Переводы строк возвращаются такими, какими их оставил патч: `apply_patch` Codex сам переписывает CRLF
  файла в LF, и прежних байтов в треде нет.
- **Ревёрт не переписывает файл треда, а заводит сегмент** `rollout-<время>-<тред>_<сегмент>.jsonl`, первая
  строка которого указывает на префикс файла, от которого отрезали (`session_meta.history_base =
  {thread_id: <ключ файла>, end_byte_offset}`; цепочки бывают, смещения ровно на границе строк - замерено).
  `thread/list` выдаёт каждый сегмент отдельной строкой с тем же id. Всё, что читает тред с диска, идёт
  через `CodexRollout` (`useLines`, `current`, `nameOf`): `transcriptFile` - новейший сегмент,
  `threadIdOf` - id треда, а не сегмента, история схлопывает строки одного id, поиск читает сохранённую
  часть предыдущих файлов и помнит сегмент в манифесте (`SearchIndex.Seen.segment`, `FORMAT` 3). Без этого
  история и поиск возвращали ровно то, что откатили.
- **Форк 0.163 ссылается на источник той же `history_base`, а не копирует его** (замерено: файл форка - строка
  `session_meta` с `forked_from_id` и базой в файл источника до места форка, и ничего унаследованного). Ключ базы -
  файл ЧУЖОГО треда (первый файл источника или его сегмент), поэтому база ищется по ключу во всей папке
  (`CodexRollout.fileByKey`), а не среди сегментов своего треда. Иначе у форка с диска не было модели, счёта окна,
  унаследованных вопросов и картинок, а поиск «этот чат» не находил того, что над швом (`SearchIndex.readKeptPart`
  читает унаследованное так же). Форк 0.160 копировал строки в свой файл - он читается как раньше.
- **Точка форка - ход**: `ForkOrigin.at` - последний ход, который форк несёт, и он же `lastTurnId` у
  `thread/fork` (форк сохраняет id унаследованных ходов - замерено). Целый форк фиксируется на последнем
  ЗАКОНЧЕННОМ ходе в момент нажатия (через идущий ход Codex форкать отказывается); форк «до сообщения» - на
  ходе перед ходом этого сообщения (`ForkOrigin.resolve` по `CodexHistory.turnRefs`); форк до первого
  сообщения не несёт ничего и поднимается обычным `thread/start`. Рождённый форк записывается в
  `ForkBook`; шов «new branch from …» в истории ставится после хода `at` (`CodexHistory.page`), у
  нерождённого - под историей источника (`forkOpening`/`forkEarlier`). Codex пишет файл форка сразу при
  `thread/fork`, поэтому «форка без треда», который у оригинала надо было поднимать заново, тут не бывает.

### Список изменённых файлов хода (из ACC 0.13.33 и 0.13.40)

Под ответом хода - список файлов с цифрами, откатом файла и всего хода, возвратом и Cmd+Z; панель и движок отката
(`ChangeRevert`, `FileReverts`) общие с оригиналом, данные под ним - Codex (подробно - `.claude/rules/changed-files.md`).

- **Удаление и перенос - правки движка** (`ChangeRevert.Edit.Delete`, `Edit.Move`): откат удалённого пишет его текст
  заново, перенесённого - снимает патчи и переносит на старое место одной командой (`FileReverts.moved`).
- **Сверка с диском в конце хода своя** (`TurnFiles`, вместо `UndiffedEdits` оригинала, который стоит на копиях
  файлов Claude Code): база - чтение файла на `item/started` первого патча (файл там ещё до патча, замер 0.163),
  принимается, только если патчи хода ложатся на неё; на конце хода (и остановленного) расхождение с диском -
  форматтер, `sed` - уходит `files_settled` перед `result`. `turn/diff/updated` для этого не годится: это сумма
  патчей, а не диск.
- **Агенту об откате говорит панель** (`PutBack`, сообщение developer через `thread/inject_items` перед следующим
  `turn/start`): Codex не замечает, что файл изменился снаружи.
- **Правки субагентов вкладки входят в список** (`CodexSession.spawned`, `subagentNotification`): пока ход родителя
  открыт - в его список, после - в список следующего хода. Учёт помощников (`onBackground`) у вкладок не включён.

### История, форки, контекст, лимиты

- **История** (`CodexHistory`): список - `thread/list` с фильтром по папке проекта, листается по
  `nextCursor`, пока не наберётся 40 строк без разговоров прогонов сценариев (`ScenarioConversations`);
  страница - `thread/turns/list` с конца, по 10 ходов на запрос, курсор - id самого старого хода; ход
  проигрывается в диалект `CodexReplay.lines`. Бюджеты страницы: стол 30 ходов / 512K символов /
  12K вывода команды, телефон 10 ходов / **128 КБ в байтах UTF-8** (кадр релея считает байты) / 2K.
  Модель разговора читается из файла треда (`turn_context`), последняя занятость контекста - из
  `token_count`.
- **Вопросы с кнопками** в `thread/turns/list` не попадают вовсе (замерено). Они есть только в файле
  треда: `function_call` `request_user_input` и `function_call_output` с ответами, связанные `call_id`
  (`CodexHistory.asksOf`). `CodexReplay` ставит вопрос перед финальным ответом хода, ответ - строкой
  человека (`toolUseResult.answers`), а ход, оборванный на вопросе без ответа, не закрывает - панель
  поднимает такой вопрос живой карточкой.
- **Картинка сообщения из истории** (превью над чипом и клик, ACC 0.13.45) читается из файла треда
  (`ThreadPictures`): предмет `item_completed` с `UserMessage` несёт картинки байтами (`image` с `image_url`) и тот
  же id, что `thread/turns/list`, то есть uuid карточки из реплея. Сообщение, отправленное в этом запуске, Codex
  знает под своим id, а панель - под своим, поэтому разговор помнит место каждого своего сообщения в ходе
  (`CodexSession.placeOf`) и ищется n-й `UserMessage` хода. Реплей не дописывает подпись `[Image #N]`, которую
  слова уже несут (`CodexDialect.missingCaptions`): панель пишет её в текст сама, и каждая картинка из истории
  была двумя чипами. Подробно - `.claude/rules/image-preview.md`.
- **Форк** получает имя родителя: Codex сам копирует его в запись нового треда, и вкладка берёт его с тем
  же происхождением (модельное остаётся модельным, остальное - человеческое, `adoptForkName`), иначе
  генератор названий перезаписывал имя, данное человеком.
- Вопрос из файла треда встаёт в истории туда, где был задан: после реплики или мысли агента, за которой
  шёл (`Ask.after`, по id из `response_item`), с временем ответа (`answeredAt`).
- **Имена**: у Codex одно поле на тред, туда пишут и модель (`CodexTitles`), и человек. Что дала
  модель, записано в `AutoTitles` (файл на проект); любое другое имя - человеческое (`TITLE_USER`) и
  выше модельного - в истории, поиске и вкладке. `thread/name/updated` с чужим именем - переименование
  в другом клиенте (`onRenamed`). Незагруженный тред переименовывается через общий процесс каталога.
- Файлы тредов - `~/.codex/sessions/ГГГГ/ММ/ДД/rollout-<время>-<uuid>.jsonl`, имена - в
  `~/.codex/session_index.jsonl`. По ним же работают поисковый индекс (`search/TranscriptText`,
  `SearchIndex`) и счётчик токенов за день (`CodexTokenUsage`).
- **Токены за день** (из ACC 0.13.44; счётчик «tok» у поля и карточка «TOKENS A DAY» статистики) читаются из файлов
  тредов, а не из ходов панели: субагенты Codex и прогоны сценариев пишут свои треды и мимо вкладок не проходят.
  `CodexTokenUsage.read` берёт события `token_count` (`last_token_usage.total_tokens` - этот запрос,
  `total_token_usage` - итог треда) по часам от начала эпохи; **повтор итога в том же файле - не запрос**: Codex
  повторяет событие, когда сменились только лимиты (замер 0.163: 72 из 5073), и без этого «tok» считал часть запросов
  дважды. Копий между файлами нет: форк и откат 0.163 ссылаются на прежний файл (`history_base`). `TranscriptTokens`
  держит книгу в `StatsLedger` (первое чтение - все файлы в несколько потоков, дальше только изменённые за двое
  суток до прошлого чтения, `SLACK_MS`), книга помнит то, чего на диске уже нет. **Архив не читается**:
  `archived_sessions/*.jsonl.zst` сжат zstd, читателя у IDE нет. Подробно - `.claude/rules/stats.md`.
- **Контекст** - из `thread/tokenUsage/updated`: занято `total - reasoning`, окно -
  `modelContextWindow`. Окно зависит от модели и режима Std/Long (`-c model_context_window` при запуске,
  `ModelContexts`; у gpt-6.1-sol Std 475 000, у остальных 258 400, Long 828 400 - уже с запасом кэша). Счёт,
  сделанный другим процессом или прочитанный из файла треда, меряется окном, в котором разговор сейчас
  (`CodexSession.contextNow`, `usageLive`): иначе после Std->Long точная цифра возвращала старое окно. Пока
  Codex не посчитал, шкала берёт окно из каталога, как чип CTX (`contextWindowOf` в `catalog.ts`, третий
  аргумент `contextOf`). Режим объявляется с `born`, как модель: объявление не стирает точную цифру.
- **Лимиты** - одна картина на аккаунт для всей IDE (`AccountUsage`), из `account/rateLimits/read`
  (весь ответ, с `rateLimitsByLimitId`) и уведомлений `account/rateLimits/updated`. Корзины, кроме
  основной `codex`, с окном - отдельные кольца (`model_scoped`, подпись - `limitName` или id словом,
  «Premium»). Уведомление про другую корзину основные кольца не трогает - картина перечитывается.
  Судьи «чужих цифр» оригинала нет: у Codex нет общего кэша, а честные ответы двух ящиков одной
  подписки он выбрасывал. Codex сообщает
  до двух окон с их длиной; окно до суток идёт на пятичасовое кольцо, длиннее - на недельное
  (`CodexShapes.usage`). У места в business-плане окон нет вовсе, есть только лимит трат, который
  задало рабочее пространство (`individualLimit`, сбрасывается раз в месяц): он едет блоком «бюджет
  сверх плана» (`extra` с `percent` и `resets`) и рисуется своим кольцом «Spending limit» под полем и
  строкой «spend» на экране аккаунтов (`spendingWindow` в `feed/usage.ts`). Уведомления бывают
  частичными, поэтому поля сливаются, а не заменяются.
- **Целый ответ и катящееся обновление различает метка перевода**: `CodexShapes.usageAnswer` пишет
  `full_answer` (и `ordinaryUsageAllowed`, если он дан), `account/rateLimits/updated` её не получает. Опустить
  процент внутри окна и снять отказ лимита может только целый ответ (ранний сброс недели кнопкой на странице
  аккаунта), `ordinaryUsageAllowed: true` снимает отказы сразу, `false` держит их до сброса. Лимит трат
  business-места без окон - лимит всего аккаунта до своего `resetsAt`, и отказ по нему
  (`workspace_*_usage_limit_reached`) берёт сброс оттуда. Подробно - `.claude/rules/indicators.md`, «Подарочный
  сброс».

### Аккаунты

- У каждого добавленного аккаунта свой `CODEX_HOME`: `~/.amazing-codex/accounts/<id>/` с его
  `auth.json` и **символьными ссылками** на всё остальное в `~/.codex` (кроме `auth.json` и баз
  `*.sqlite*`); `CODEX_SQLITE_HOME` указывает на обычный `~/.codex`. Так вход у аккаунтов разный, а
  история, конфиг, скиллы, промпты и MCP-серверы - общие (`AccountDrawer.sync`).
- В окружении процесса аккаунта `OPENAI_API_KEY`, `CODEX_API_KEY` и `CODEX_ACCESS_TOKEN`
  выставляются **пустыми**, а не выбрасываются: окружение ребёнка собирается поверх родительского, и
  выброшенный ключ вернулся бы оттуда и перебил выбранный аккаунт.
- **Удалять ящик - только `AccountDrawer.delete`** (NIO, без перехода по ссылкам). Котлиновский
  `deleteRecursively` идёт по символьным ссылкам и снёс бы `~/.codex/sessions` - всю историю машины.
  Держит это тест.
- Имя и план строки - из `auth.json` ящика (`AccountIdentity`: клеймы ID-токена `email` и
  `chatgpt_plan_type`; ключ API на экране - последние четыре символа, а в записи - отпечаток всего
  ключа, чтобы два ключа с одним хвостом не стали одним аккаунтом). Токен только читается локально.
  Личность читается из файла сразу (`probe`/`identityOf`), без процессов и окон свежести оригинала;
  ключи в системном keyring файла не оставляют - тогда адрес берётся из `account/read`, без рабочего
  пространства, и такой ящик никогда не заменяется по догадке (`Holds.Unknown`).
- Логика записей - оригинала (непрозрачные id с `key`, `renew`/`refile`, слияние дублей), но с
  условием Codex: `auth.json` называет аккаунт, даже если токен отозван. Поэтому вход-дубль обычного
  входа отклоняется, а дубли сливаются **только если оставляемый вход недавно ответил о лимитах**
  (`AccountUsage.provenSince`, `CodexAccounts.credentialWorks`) - иначе удалился бы единственный
  рабочий вход.
- Вход - `codex login` во встроенном терминале с `CODEX_HOME` ящика (`AccountSignIn`), выход -
  `codex logout`.
- На Windows ссылки могут не создаться (нет прав на symlink); тогда проба (`IsolationProof`)
  выключает добавление аккаунтов, а не работает на наполовину собранном ящике.
- Экран аккаунтов (ACC 0.13.43) показывает у каждой цифры время до сброса окна, а у аккаунта на пределе - когда он
  снова примет работу (`usableAgainIn` в `feed/usage.ts`), включая business-место с исчерпанным лимитом трат;
  `ordinaryUsageAllowed: true` строку снимает.

### Работу, остановленную не человеком, панель продолжает сама (из ACC 0.13.42)

Смена аккаунта посреди хода и отказ лимита останавливают работу, которую никто не просил останавливать. Codex к тому
же отдаёт агенту любую остановку как `<turn_aborted>` - «The user interrupted the previous turn on purpose», и
агент стоит, как будто остановил человек. Поэтому следующее слово говорит панель (подробно - `.claude/rules/accounts.md`,
«Работу, которую остановил не человек»):

- **Учёт - `CarryOns`** (чистые функции с тестами), дороги - `CodexSessions`, что и когда сказать -
  `CodexSessionHub.carryOn`/`noteLimitRefusal`/`carryOnChanged`, слова на языке панели - `CarryOnWords`. Слова едут
  внутри `<panel-carry-on reason="...">`: лента и история рисуют такую карточку «PANEL», а не «YOU», поиск её не
  индексирует (`TranscriptText.personWords`), вкладка по ней не называется.
- **Смена аккаунта** (`ACCOUNT_SWITCH`): метка ставится в момент прерывания (`turn/interrupt`), только над ходом,
  который Codex правда ведёт (`CodexSession.runsATurn`); план, ждущий решения, не прерывается, а переезжает с
  разговором (`HeldPlan`). Новый процесс делает `thread/resume`, своего хода восстановления Codex не запускает
  (замер 0.163) - «продолжай» говорит панель. Написанное в прерванный ход и не принятое `turn/steer` уезжает тоже
  (`takeUnsent`/`adopt`).
- **Лимит** (`LIMIT`): продолжение через 30 секунд после сброса окна (`LimitRelief.RESET_SLACK_MS`), сброс неизвестен
  - через 15 минут с пометкой «пробую». Окно дольше шести часов не ждётся (`LIMIT_WAIT_MS`), три отказанных
  продолжения подряд - вкладка остаётся человеку (`LIMIT_TRIES`). **Не ждутся отказы, которые не кончаются по часам**
  (`CarryOns.endsOnAClock`): кредиты рабочего пространства (`workspace_*_credits_depleted`,
  `CodexShapes.CREDITS_REASONS`) и бюджет самой сессии (`CodexErrors.SESSION_BUDGET`). Лимит трат business-места
  ждётся по общему правилу: сброс месячный, и шесть часов его отсекают.
- **Признак «ход прошёл» у форка свой** (`refusedTurns` в `CodexSessionHub.noticeLimit`): результат хода, которому
  отказал лимит или вход, у Codex нарочно не ошибка (`is_error: false` - отказ сказан заглушкой `<synthetic>`), и по
  одному результату каждый отказанный «продолжай» считался прошедшим ходом. Теперь ход прошёл, если в нём не было
  заглушки отказа и результат не ошибка; диалект не тронут.
- **Третья дорога оригинала, `RESTART`** (перезапуск под работающими фоновыми агентами), у вкладок форка закрыта и
  оставлена ради слияний: о субагентах Codex вкладке не говорят (`onBackground` только у карточки сценария), и
  `pendingAgents` всегда пуст.
- Строка плана в конце ленты (`carryOnWait`, `CarryOnRow`, кнопка «Don't carry on» → `cancelCarryOn`, телефону
  разрешено), момент едет полем `until`. «Не продолжать» и Stop снимают слова, а не ожидание: очередь всё равно ждёт
  сброса. Говорится из `runQueued`, первым и мимо придержанной очереди; один проход на вкладку (`PassGate`).
  Ожидание не переживает перезапуск IDE - таймеры в памяти.
- Сквозной тест - `CarryOnFlowTest`: настоящий хаб над поддельным `codex app-server` (`FakeCodex`, скрипт на `sh`
  через `CodexPreferences.executablePath`), уровнем ниже - `CarryOnSessionsTest`, `HeldPlanMoveTest`.

### Клавиши панели и закрытые вкладки (из ACC 0.13.30 и 0.13.40)

- **Клавиши - действия IDE, а не слушатель на странице** (`PanelKeys`, `plugin.xml`): IDE получает нажатие раньше
  браузера панели. Следующая и предыдущая вкладка и закрытие берут клавиши самой IDE (`use-shortcut-of`:
  `NextTab`, `PreviousTab`, `CloseContent`), новая вкладка - Cmd+T / Ctrl+T, возврат закрытой - Cmd+Shift+T /
  Ctrl+Shift+T, очередь - Alt+Enter. Обёртки висят на компоненте браузера и выигрывают только при фокусе в панели,
  вне её действия выключены. Шпаргалка - «Settings → Keyboard shortcuts» (`KeysScreen.tsx`). Id действий пришли
  слиянием с именами оригинала (`AmazingClaudeCode.*`) - см. `.claude/rules/panel-keys.md`. В песочнице клавиши
  проверяются настоящими нажатиями, а не через CDP: `Input.dispatchKeyEvent` идёт мимо диспетчера IDE. Ctrl+V на
  Linux панель тоже берёт из раскладки IDE (`PasteKeys`).
- **Закрытая вкладка возвращается** (`ClosedTabs` в хабе, до 20 назад; список «Recently closed» сверху истории;
  переживает перезапуск IDE через `TabMemory.State.closed`). Возврат - то же восстановление, что после перезапуска
  (`bringBackClosed`): модель, усилие, окно, режим и быстрый режим свои, черновик, место в полосе, форки под ней. Файл
  треда спрашивается до возврата (`CodexHistory.transcriptFile`): тред могли архивировать или удалить в другом
  клиенте. Процесс закрытой вкладки замолкает в момент закрытия (`CodexSession.mute`). **Очередей возвращается две**,
  обе придержанными до следующего сообщения человека: очередь хаба и то, что написали в идущий ход, а `turn/steer`
  не принял (`CodexSession.unsent`, `keepClosed`, `ClosedTabUnsentTest`). Подробно - `.claude/rules/reopen-tabs.md`.

### MCP и плагины

- Статус - `mcpServerStatus/list` + `codex mcp list --json` (настроенные, включая выключенные) +
  уведомления `mcpServer/startupStatus/updated`; слова статуса - как ждёт панель (`connected`,
  `needs-auth`, `failed`, `pending`, `disabled`).
- Добавить / убрать - `codex mcp add` / `codex mcp remove`, после чего разговор перезапускается над
  тем же тредом (ждёт конца идущего хода), как в оригинале. Кнопка переподключения -
  `config/mcpServer/reload`: переподключения одного сервера у Codex нет, перечитываются все.
- Вход в сервер - `mcpServer/oauth/login`: адрес открывается в браузере машины. С телефона не
  выполняется - колбэк приходит на порт этой машины.
- Плагины - `codex plugin list/add/remove`. **Включать и выключать плагин Codex не умеет**, и панель
  на это честно отказывает, а не делает вид.

Приложения плагинов показываются внутри карточки установленного плагина (`CodexApps`,
`PluginAppsDesk`, общий компонент `PluginApplications` для панели и телефона). Их связь с плагином
берётся из `plugin/read`: `apps` и материализованные `appTemplates`, с причинами ограничений рабочего
пространства. Для локальных маркетплейсов путь берётся из `plugin/list` с фильтром `local`; полный
удалённый каталог для этого не нужен. `app/read` даёт метаданные и `installUrl`, `app/list` даёт
`isAccessible`, а `app/installed` даёт эффективные `enabled` и `callable`. При обновлении каталог
перечитывается с `forceRefetch: true` один раз, следующие страницы читаются из того же кэша.

У Codex 0.160.0 эти поля не подтверждают успешный вход во внешний аккаунт. Панель так и пишет:
доступность инструментов показана отдельно, а `USER_NOT_LOGGED_IN` последнего вызова с
`appContext.connectorId` отмечает необходимость входа. «Подключить» открывает HTTPS-адрес, выданный
Codex, через браузер IDE. При возвращении в IDE и по кнопке проверки выполняется
`app/installed {forceRefresh: true, threadId}` в процессе текущего разговора: он публикует свежий
набор инструментов без нового чата или остановки хода. У вкладки без процесса проверка работает
через `CodexOneShot`, без хода модели. Отмена прекращает ожидание панели и открытие ещё не
отправленного в браузер адреса, но не отзывает подключение в браузере. Смена аккаунта отбрасывает
старые ответы и адреса; в браузере нужен тот же аккаунт ChatGPT, что выбран в Codex. Телефон читает
состояние основной вкладки проекта и предлагает подключиться из IDE, адрес ему не передаётся.
Контракт протокола: https://learn.chatgpt.com/docs/app-server (раздел Apps).

## Что не перенесено и почему

- **Экран «Settings sources» оригинала** (выбор слоёв настроек Claude Code) - у Codex флага слоёв нет
  и не нужно: слой проекта грузится только у доверенного проекта, а ключи провайдера и адреса
  (`model_provider`, `openai_base_url` и т.п.) Codex из проектного конфига выбрасывает сам (замерено).
  Вместо экрана - доверие проекту и строки в ленте (см. «Настройки Codex и доверие проекту»).
- **Ложное «exit code 137» при плановом рестарте** - в форке его не бывает: флаг остановки живёт в
  каждом `AppServer`.
- **`JournalStrands`** перенесён как есть, но у Codex всегда отвечает «не нить»: потока отчётов флота нет,
  события субагентов отсекаются по треду, а `parent_tool_use_id` несут только результаты их патчей - строки
  списка файлов хода, которые нитью нарочно не считаются (иначе телефон, прореживая шаги, терял бы файлы).
- Идентификаторы общего кода панели оставлены как в оригинале (`--acc-*`, `ClaudePreferences` в
  комментариях, коды вроде `noClaude` в очереди сценариев - он хранится в файлах на диске), чтобы
  следующие слияния с оригиналом шли чисто. Исключение - экран настроек: `CodexConfig.tsx`,
  сообщения `askCodexConfig`/`setCodexConfig`/`codexConfig`, экран меню `codexConfig`.

- **Вход в Claude Design** (`/design-login`, `DesignLogin`) - у Codex такого нет; удалено вместе с
  кнопкой на экране аккаунтов и сообщением протокола.
- **Остановка одной фоновой задачи** (`stopTask`) - у `app-server` нет такого запроса; отвечает
  отказом.
- **Число сообщений в строке истории** - `thread/list` его не отдаёт, строка показывает только то,
  что известно.
- **Страница в маркетплейсе** не заведена: это решение владельца. Картинки для неё снимаются тем же
  процессом, что у оригинала (скилл `/listing-shots`, `scripts/listing/`, `.claude/rules/listing-screenshots.md`),
  в `~/Downloads/amazing-codex-listing`.
- **Моды Claude Code** (ACC 0.13.27: `ModLines`, `ModStates`, `AddedCommands`) - у Codex такого нет. Части
  панели (`ModDock`, `feed/mods.ts`, «A MOD ASKS») взяты как есть ради чистых слияний и молчат: IDE таких
  строк не шлёт.
- **Релей у форка свой, а не оригинала** - `wss://relay-codex.mzpizote.com` (`RemoteAgent.DEFAULT_RELAY`,
  приложение `acx-relay` в Coolify). Он раздаёт телефону клиента форка (манифест Amazing Codex, иконки
  ACX) и `/privacy` из `PRIVACY.md` форка. Сохранённый в настройках адрес релея оригинала считается
  старым умолчанием и не держит (`RemoteAgent.chooseRelay`); спаренные через оригинал телефоны
  спариваются заново. Dev-релея на сервере нет: локально - `./scripts/relay-dev.sh` (:4450), выкатка -
  `./scripts/relay-deploy.sh`, который до сборки проверяет, что цель - приложение форка, а в
  `relay/public/` - клиент форка. Подробности - `docs/panel-notes.md` («Свой релей форка») и
  `relay/README.md` (первичная настройка - «First deploy»).
- Релей развёрнут 2026-10-02: приложение Coolify `acx-relay` (uuid в `scripts/relay-deploy.sh`), ключи
  VAPID - в `secrets/relay-vapid.env` (в git не едет, значения в чат не выводить). Логи релея хранятся
  7 дней, как обещает `PRIVACY.md`: docker сервера режет их только по размеру, поэтому срок держит
  `container-log-retention.py` на сервере раз в час (`/etc/cron.d/relay-log-retention`). Заводишь
  форку ещё один релей - впиши его uuid туда же, иначе обещание политики для него станет неправдой.
- `PromptDeliveries` и часть `PromptDelivery` остались от оригинала: там проверка доставки читала
  транскрипт CLI. У `app-server` доставку подтверждает сам ответ на `turn/start` / `turn/steer`, и
  живой код их не зовёт.

Из ACC 0.13.29-0.13.45 (перенос - `docs/catch-up-acc-0.13.45.md`):

- **Копии файлов Claude Code для сверки хода** (`UndiffedEdits`, ACC 0.13.40) - у Codex копий нет; сверка своя
  (`TurnFiles`, «Список изменённых файлов хода»).
- **Досчёт большой правки без диффа** (ACC 0.13.33: CLI не кладёт `structuredPatch` у больших правок, и цифры
  считались по `originalFile`) - каждый `fileChange` Codex несёт патч целиком, досчитывать нечего.
- **`ForkLineage`** (страница форка, дошедшая до верха своего файла, продолжается в источнике; хвост компакта один
  раз) - форк Codex отдаёт унаследованные ходы своим `thread/turns/list`, а файл форка 0.163 дочитывается по
  `history_base` (`CodexRollout.fileByKey`).
- **Метка окна в имени модели** (`[1m]`, строка-вложение `model` с `identity.modelId`, `modelIdentity`) и выученные
  окна из `result.modelUsage` (`learnWindows`) - у Codex окно - режим Std/Long вкладки и каталог; ветки панели молчат.
- **Адрес для других сессий в `/status`** (реестр CLI `sessions/<pid>.json`) - у Codex нет ни реестра, ни
  инструментов переписки между тредами; в карточке id треда и `codex resume`.
- **Причина «перезапуск под фоновыми агентами»** (`RESTART` у автопродолжения) - у вкладок инертна, `pendingAgents`
  пуст (см. раздел про автопродолжение). Сигналы фоновых задач CLI (`background_tasks_changed`, `owned_by_subagent`,
  фоновые команды помощников) Codex не шлёт - у сценария работают только пары `task_started`/`task_notification`,
  которые говорит переводчик.
- **Архивные разговоры в токенах за день** не считаются: `archived_sessions/*.jsonl.zst`, читателя zstd нет.
- **Дедуп копий одного ответа по `message.id` + `requestId`** (счёт токенов оригинала) - у Codex задача другая:
  повтор итога `token_count` в том же файле.
- **Кэш расхода в своём конфиге и судья чужих цифр** (`usageProbeEnvironment` с отдельной папкой, `UsageProbes.trust`)
  - у Codex кэша нет, лимиты спрашиваются у бэкенда для входа ящика.

## Как проверять

- Статистика из песочницы уходит на `http://localhost:8082` (общий сервис из репозитория оригинала,
  `pnpm dev:usage` там), а не в боевой; `-PusageUrl`/`-PusageKey` направляют её в другое место.
- `./gradlew test` - движок, перевод, аккаунты, история, сценарии. После смены сигнатуры в
  `src/main` (например, нового параметра конструктора) тестовые классы могут остаться собранными против
  старой и упасть с `NoSuchMethodError`: тогда сначала `./gradlew compileTestKotlin --rerun`, потом
  отдельно `./gradlew instrumentCode instrumentTestCode` и `./gradlew cleanTest test`. В одной команде
  с `--rerun` шаги инструментации падают на ошибке плагина платформы («doesn't support the nested
  "skip" element») - это не поломка проекта.
- **Поддельный `codex app-server`** (`src/test/.../codex/FakeCodex.kt`): скрипт на `sh`, ставится настройкой пути к
  исполняемому файлу (`CodexPreferences.executablePath`, смотрится раньше всего на машине), отвечает на рукопожатие,
  `thread/start`/`resume`, `turn/start`, `turn/steer` (отказ или приём) и пишет каждую строку, поэтому тест проверяет,
  что дошло до Codex, а не только что сказали экранам. Что Codex говорит сам (начало и конец хода, лимиты), тест
  говорит через `CodexSession.heardFromCodex`. На нём стоят `CarryOnFlowTest`, `CarryOnSessionsTest`,
  `HeldPlanMoveTest`, `ClosedTabUnsentTest`, `FastModeSessionsTest`, `ModelOnWireSessionsTest`, `FilesPutBackTest`,
  `SubagentChangesTest`, `EditorOnceTest`, `SaidPictureTest`, `SessionInfoTest`, `TurnEndOrderTest`. Файлы, которые
  тест пишет, кладутся под `FileUtil.getTempDirectory()`: папка лёгкого проекта после первого теста не разрешённый
  корень VFS.
- Живой тест против настоящего Codex (тратит ходы аккаунта, поэтому выключен по умолчанию):
  `echo gpt-5.6-luna > /tmp/acx-live-codex && ./gradlew test --tests '*CodexSessionLiveTest*'`, после
  прогона файл удалить. Проверяет ответ, инструменты, одобрение в режиме «Ask every time», продолжение
  треда в новом процессе и чтение его из истории, а второй тест - откат (ревёрт, возврат файла, отказ при
  непросмотренном сообщении, история из сегмента) и форк через выбранный ход.
- `cd webview && pnpm tsc --noEmit && pnpm lint && pnpm vitest run` - панель. `pnpm lint` - oxlint с
  одним правилом, порядком хуков React (`.oxlintrc.json`): хук ниже раннего `return` ронял всю панель
  на старте (ошибка React #310), а видно это было только запуском. ESLint тут не работает: TypeScript 7
  без JS API, разборщику TypeScript для ESLint не на чем стоять. Сборка панели и телефона и `pnpm test`
  зовут `pnpm lint` сами.
- Харнесс: `cd webview && pnpm dev`, затем http://localhost:5190/harness.html - настоящий `App` без
  агента и без IDE (как устроен - в `docs/panel-notes.md`, раздел про харнесс).
- Песочница: `./scripts/sandbox.sh` - собирает плагин и поднимает отдельный WebStorm на
  `sandbox-project/` (лог - `build/sandbox.log`). Полка сценариев песочницы
  (`sandbox-project/.codex/scenarios/`) пустая и не в git: сценарий для проверки пишется на месте,
  кнопкой «New scenario» или фразой в модель. Песочница гасит только свою копию (маркер
  `io.github.crmapache.amazingcodex`), песочницу оригинала не трогает.
- **Живой прогон панели в песочнице агентом**: `./gradlew runIde -PopenProject=$PWD/sandbox-project
  -PjcefDebugPort=4452`, затем Playwright `chromium.connectOverCDP('http://127.0.0.1:4452')` и страница с
  адресом `acx-webview` (у README в редакторе своя страница JCEF - не перепутать). Кнопки - по ролям и
  именам из `ariaSnapshot()`. Модальное окно самой WebStorm (например, «Evaluation Feedback») молча держит
  действия IDE: файл из ленты не открывается, пока его не закрыть (`osascript`, кнопка по `description`).
  Телефон к такой песочнице спаривается через ссылку `.../p#...` с экрана Remote access и «Allow» в IDE.
- Скриншоты для стора: `scripts/screenshots.mjs` (харнесс на :5190, кадры из
  `webview/src/harness/scenarios/showcase.ts`); телефон снимается настоящим клиентом через релей.
- Протокол `app-server` своей версии Codex можно выгрузить схемой:
  `codex app-server generate-json-schema --out /tmp/codex-schema` - это самый надёжный ответ на
  «какие поля у этого уведомления».
