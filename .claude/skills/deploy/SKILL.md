# Релиз плагина

Запуск `/deploy` - это и есть разрешение на коммит, пуш и публикацию: проектное
правило «коммиты только с явного разрешения» этой командой и снимается. Ничего
не переспрашивай, доводи до опубликованной версии.

Останавливайся молча только там, где идти дальше нельзя (см. «Когда стоп»).

**Релиз - это ДВА артефакта, а не один.** Плагин уезжает в Marketplace, телефонный
клиент - на релей, и они собираются из одного и того же `webview/`. Шаг 7 не
опциональный и не «если трогали телефон»: панель и телефон делят `feed/`,
`protocol.ts` и словари, так что почти любая правка меняет обоих. Плагин без
релея - это телефон, говорящий со вчерашним экраном по сегодняшнему протоколу.

Третий - сервис статистики (шаг 5), и про него решает не память, а сервер: шаг
сравнивает его исходники с тем, что там собрано, и выкатывает, если разошлись.

**Субагентов не запускать** - ни `cp-committer`, ни любых других. Текст коммита и
пункты CHANGELOG пишутся из знания того, что было сделано в этой сессии; агент
вхолодную вычитает тот же дифф заново и напишет хуже.

**Вывод пользователю - по скиллу `human-output`:** коротко, что выпущено и куда.

## Arguments

$ARGUMENTS

Пусто - поднимаем патч (0.7.9 → 0.7.10). `minor` / `major` - соответствующую
часть. Точная версия (`0.8.0`) - берём как есть.

## Шаг 1. Контекст (один вызов)

```bash
echo "== branch =="; git branch --show-current; \
echo "== version =="; grep '^version' gradle.properties; \
echo "== status =="; git status --short; \
echo "== unreleased commits =="; git log --oneline "$(git log -1 --format=%H --grep='^chore: bump version')"..HEAD; \
echo "== diff =="; git diff --stat; \
echo "== secrets present =="; grep -c '^export ACC_PUBLISH_TOKEN=' .env
```

В релиз войдёт всё сразу: незакоммиченные правки **и** коммиты после прошлого
bump. Про них и пишется CHANGELOG.

`.env` дальше не читай ничем: ни целиком, ни выборочно. Проверка наличия -
только счётчиком строк, как выше (правила в `CLAUDE.md`, раздел про секреты).

## Шаг 2. Проверки

```bash
cd webview && pnpm tsc --noEmit && pnpm lint && pnpm vitest run; cd ..
cd ../amazing-claude-code && pnpm --filter amazing-claude-code-usage test; cd ../amazing-codex
./gradlew test --console=plain
```

Упало - стоп: сломанную версию в стор не отправляют. Сервис статистики общий для
обоих плагинов и живёт в репозитории оригинала (`../amazing-claude-code/usage-service`,
см. «Правила проекта» в `CLAUDE.md`), поэтому и тест его - там. Его
`codexFork.test.ts` читает каталог фич, экранов, настроек и команд этого рабочего
дерева (`src/main/kotlin/.../usage/`) и падает на новой фиче без подписи в сервисе -
так она ловится до публикации, а не пропадает из админки. Подпись добавляется в
`usage-service` оригинала, это разрешённое исключение из «оригинал не трогать».

Проверки форка, пропущенные с пометкой «the Codex fork's ... is not there yet»,
значат, что тест не нашёл форк рядом с оригиналом: это не зелёный результат, а
непроверенный. Тогда стоп, как при падении.

## Шаг 3. Версия и CHANGELOG

1. `gradle.properties`: `version = X.Y.Z`.
2. `CHANGELOG.md`: новый раздел сразу под `## [Unreleased]`:
   `## [X.Y.Z] - YYYY-MM-DD` (дата локальная, `date +%F`).
3. Внизу файла: в строке `[Unreleased]` подменить прошлую версию на новую и
   добавить строку сравнения для новой - ровно как у предыдущих версий.

Раздел обязан называться точно как версия в `gradle.properties`: сборка берёт в
описание обновления именно его, а не найдя - `Unreleased` (см. `changeNotes` в
`build.gradle.kts`).

**Как писать пункты** (стиль задан прошлыми релизами, посмотри соседние разделы):

- Английский, по пункту на изменение, простым списком без подзаголовков.
- «Fixed: <что видел человек> ... <почему так было и что теперь>». Сначала
  симптом его словами, потом причина - одним-двумя предложениями.
- Про поведение, а не про код: ни имён файлов, ни классов, ни функций.
- Тире не ставить, только обычный дефис.
- Изменение, которое человек не заметит (рефакторинг, тесты), в список не идёт.

## Шаг 4. Коммиты и пуш

Два коммита, как в прошлых релизах:

1. Правки по сути - `fix(область): ...` / `feat(область): ...` с телом, которое
   объясняет причину поломки, а не перечисляет файлы. Только если в рабочем
   дереве есть незакоммиченные правки кода; чужие неотслеживаемые файлы, не
   относящиеся к работе, не добавляй - скажи о них в конце.
2. `chore: bump version to X.Y.Z` - `gradle.properties` и `CHANGELOG.md`.

Затем `git push origin main`.

## Шаг 5. Сервис статистики (если разошёлся с сервером)

Плагин шлёт анонимную статистику в `usage.mzpizote.com` (`UsageSender.DEFAULT_URL`),
а сервис молча выбрасывает имена, которых не знает: новая фича, настройка или
команда считается, только когда выкачен сервис с её подписью. Поэтому он идёт
**до** публикации плагина, а не после.

Сервис один на оба плагина (поле `product`: `acc` / `acx`), его исходники - в
`../amazing-claude-code/usage-service/` (памятка - его `README.md`), приложение
Coolify одно - `acc-usage`. Поэтому сравнение и выкатка идут оттуда, а не из этого
репозитория: своей копии сервиса у форка нет.

Выкатывать или нет, решает сравнение с сервером, а не дифф релиза: так ловится и
выкатка, забытая в прошлый раз, в том числе релизом оригинала. Так и было у
оригинала: подпись выключателя орфографии из 0.13.32 доехала до сервиса только
вместе с 0.13.33.

```bash
cd ../amazing-claude-code/usage-service && diff \
  <(find src package.json tsconfig.json Dockerfile -type f | sort | xargs shasum -a 256) \
  <(ssh root@40.160.85.25 'cd /root/apps/acc-usage && find src package.json tsconfig.json Dockerfile -type f | sort | xargs sha256sum') \
  && echo "== usage-service: как на сервере =="; cd ../../amazing-codex
```

Это ровно то, из чего собирается образ. «Как на сервере» - шаг пропускается.
Есть строки - сначала посмотри, чьи это правки:

```bash
git -C ../amazing-claude-code status --short -- usage-service
```

Образ собирается из рабочего дерева оригинала, а коммит там - не часть `/deploy`
форка. Пусто - разошёлся закоммиченный код, выкатывай. Есть строки и это подписи
фич форка, добавленные в этой же работе, - выкатывай и скажи в отчёте, что в
оригинале они не закоммичены. Чужая незаконченная работа оригинала - не выкатывай
(это шаг его релиза) и скажи об этом; плагин всё равно публикуй.

```bash
cd ../amazing-claude-code/usage-service && COPYFILE_DISABLE=1 tar czf /tmp/usage.tgz --exclude=node_modules --exclude=dist --exclude=data . && cd ../../amazing-codex
scp /tmp/usage.tgz root@40.160.85.25:/root/apps/
ssh root@40.160.85.25 'cd /root/apps/acc-usage && rm -rf dist src && tar xzf ../usage.tgz && \
  docker build -t 127.0.0.1:5000/acc-usage:local . && docker push 127.0.0.1:5000/acc-usage:local'
python3 ~/Documents/railway-migration/scripts/cool.py POST \
  '/deploy?uuid=jmjcoujb356netmikobqi5a0&force=true'
```

Строки `Ignoring unknown extended header keyword 'LIBARCHIVE.xattr...'` от `tar` на
сервере - безвредный шум от атрибутов macOS, на распаковку не влияют. UUID
`acc-usage` может устареть - тогда перечитай его:
`python3 ~/Documents/railway-migration/scripts/cool.py GET /applications`.

**Проверить, что встал новый образ:**

```bash
ssh root@40.160.85.25 'docker ps --format "{{.Names}} {{.Status}}" | grep jmjcoujb'
curl -s https://usage.mzpizote.com/v1/info
```

В имени контейнера - время деплоя (UTC), статус `Up` на минуты и `(healthy)`, а
`info` отвечает `"admin":true` и `"products"` с `acx`. Coolify меняет контейнер не
мгновенно: если там ещё старый, подожди минуту-другую.

Упал - плагин всё равно публикуй: цена - счёт новых фич теряется, пока сервис не
выкатят, а не сломанный релиз. В отчёте скажи об этом прямо.

## Шаг 6. Публикация

```bash
source .env && ./gradlew publishPlugin --console=plain
```

Без `--info` и `--debug`, без `env`/`printenv` до или после: в окружении лежат
токен и ключ подписи. Сам вывод задачи секретов не печатает - не расширяй его.

Задача сама собирает, подписывает и загружает архив. `BUILD SUCCESSFUL` -
версия ушла на модерацию, в списке обновлений появится через минуты-часы.

## Шаг 7. Релей и телефонный клиент (обязательно, каждый релиз)

Кода релея в GitHub нет, поэтому автодеплоя у него тоже нет - выкатывается руками.
Релей у форка свой: `wss://relay-codex.mzpizote.com`, приложение Coolify `acx-relay`.
На том же сервере живут два релея оригинала (`relay.mzpizote.com`, `relay-dev`), и
руками собранные команды из скилла оригинала положили бы телефон форка к его
телефонам. Поэтому только скрипт форка:

```bash
./scripts/relay-deploy.sh --yes
```

Он сам собирает телефонный клиент из `webview/`, проверяет, что в `relay/public/`
лежит клиент форка, а приложение в Coolify отвечает на домене форка и тянет его
образ (чужой uuid отклоняет, а не выкатывает), собирает образ на сервере, ждёт
конца выкатки и сверяет, что домен отдаёт ровно собранный бандл. Последняя строка
`==> up: relay-codex.mzpizote.com serves assets/mobile-...js` - доехало. Полная
памятка - `relay/README.md`, общие правила по серверу - скилл `infra`.

`--yes` нужен, потому что без терминала скрипту некого спросить. Сам запуск
`/deploy` и есть это разрешение.

**Телефон надо перезагрузить.** Он держит прошлый клиент service worker'ом, поэтому
в заметках релиза про это есть отдельная строчка - не забывай её, если менялся
телефонный экран.

## Когда стоп

- Ветка не `main` - релизы идут только с неё.
- Проверки из шага 2 упали.
- `ACC_PUBLISH_TOKEN` в `.env` не найден - публиковать нечем.
- Версия в `gradle.properties` уже описана разделом в `CHANGELOG.md`: её,
  похоже, уже выпустили. Скажи об этом вместо второй публикации того же номера.

Шаги 5 и 7 в этот список не входят. Упавший деплой релея - это не отменённый
релиз, а невыехавший телефонный клиент, упавший сервис статистики - недосчитанные
новые фичи. Скажи об этом прямо и отдельно, вместе с тем, на каком шаге встало.

В отчёте пользователю сервис статистики упоминается всегда: выкачен или «как на
сервере, не трогал».
